## 1. 当前结论与检查边界

MarketFlow 是面向日本门店的经营管理系统，使用 FastAPI、异步 SQLAlchemy、MySQL 和 Vue 3。已经具备“供应商商品目录 → 进货 → 签收入库 → 批次库存 → 折扣销售 → 成本/毛利报表”的核心业务闭环，同时实现了员工管理、联络事项、多门店/总部管理和需人工确认的 AI 助手。

本次检查涵盖项目结构、Git 历史、后端路由/服务/数据访问/模型/权限、前端路由/页面/API/状态、迁移、脚本与 CI；执行了自动化检查和数据库查询。没有恢复原电脑的聊天记录，也没有完整的原始需求清单，因此不虚构整体完成百分比。以下“已实现”表示有对应实现，“已验证”仅限明确列出的验证范围。

## 3. 必须保留的业务约定

- 时间基准为 `Asia/Tokyo`；销售创建限制在 09:00～21:00，销售时间由服务器产生。
- 订货截止为预计到货日前两天的 12:00，达到该时刻即禁止订货。例如 10 月 6 日到货，10 月 4 日 11:59:59 可订，12:00 不可订。前端每秒刷新锁定状态，后端再次校验。
- 自动签收每日 12:00；批次状态每日 00:05 刷新；营业时间每半小时检查库存一致性；联络事项截止检查每分钟运行。调度器启动会补处理。
- 签收将供应商商品转换/关联为正式商品，并生成批次；当前一条进货明细最多对应一个库存批次。进货状态只有待到货与已到货。
- 销售先扣最早到期批次，同到期日优先更早到货；当天到期仍可售，过期不可售。跨批次成本分别保存。
- 商品汇总库存可能包括仍未废弃的过期库存，不能拿它代替批次计算的可售库存。人工批次调整不能超过到货初始数量。
- 折扣不叠加，选最低成交价，不能通过“折扣”提高售价；历史交易保存价格、成本、名称和折扣快照。
- 金额使用 Decimal/Numeric；营业额减销售成本得到毛利润，当前不是包含工资、租金等费用的净利润报表。
- 店长管理本店；正式员工的多项维护限制在本部门；契约工权限较少，不能按正式员工权限处理。具体操作必须复用后端服务鉴权。
- 普通员工可跨店查看商品/库存/经营数据，但跨店不能写；员工私人资料不能跨店读。总部负责公司管理，不执行门店日常业务。
- 请求的 `X-Store-ID` 是读取范围，不是授权凭据；后端根据最新员工身份校验，SQLAlchemy 查询与写入事件补充门店隔离。
- 商品与折扣规则修改使用 `version/expected_version`，过期版本返回 409；进货和销售使用客户端 UUID 避免重试重复提交；库存和签收使用数据库事务与行锁。
- 联络事项发布后的正文先撤回再修改重发；普通接收人只能看自己的确认情况，发布者/有管理权限者才能看完整名单；关闭后仍允许补确认。
- AI 修改必须由本人确认，确认时重查权限、门店、过期与状态。AI Key 在服务器按员工加密保存；员工调店或切换查询店后，原会话访问受门店条件限制。
- 未配置 Redis 时使用进程内缓存，分布式锁退化为允许执行，应只运行一个调度进程；生产 Compose 把调度器独立运行。

## 6. 初次检查发现的问题和缺口（修复状态见顶部）

### P1：总部“全公司”报表的请求范围被覆盖（已复现）

`frontend/src/views/StoresView.vue` 的 `loadCompanyReport()` 显式设置 `X-Store-ID: all`，但 `frontend/src/api/http.ts` 请求拦截器无条件用浏览器保存的当前门店覆盖该头。

本次在 Node 中执行真实拦截器逻辑，输入 `all`，输出 `1`。因此总部页面显示“全公司”时，请求实际可能只查选中的门店；当前只有一家店的数据掩盖了这个错误。修复方向：保留调用方显式请求头，默认门店只在未指定范围时填入，并加入回归验证。

### P1：多门店/总部/持久 AI 的专项回归不足

测试目录没有针对 `store_policy.py`、总部门店管理和持久会话的完整专门测试；身份依赖测试还会 Mock 门店上下文配置。现有 MySQL 测试也没有覆盖两店数据隔离。因此最近新增的复杂权限功能虽已实现，验收证据仍薄弱。

建议覆盖：A 店员工读 B 店业务但不能写；员工私人资料不可跨店；总部可汇总但不能结账/入库；部门停用前的业务阻塞条件；员工调店后的会话和待确认 AI 操作失效；并发结账/签收/AI 确认只执行一次。使用隔离测试数据库，不扩写现有演示库来替代自动化测试。

### P2：进货管理列表只加载前 100 条

`ProcurementView.vue` 的 `loadAll()` 为供应商、商品目录和进货单分别请求 `page_size: 100`，只保存 `items`，没有对应服务端分页翻页。当前已有 836 张进货单，筛选后的结果超过 100 时无法浏览全部记录。目录超过 100 个时也会影响选择。应接入真实分页或明确分批加载；七天订货计划自身是另外的接口。

### P2：总部汇总日期使用浏览器本地时区

`StoresView.vue` 用 `getFullYear/getMonth/getDate` 组装日期，没有复用已有日本时间工具。非日本时区浏览器可能查询错日期；“近 60 天”使用减 60 天再含起止日的方式，日期天数口径也需明确。

### P2：前端检查没有接入 CI

当前 GitHub Actions 只检查 Python 依赖、lint/format、MyPy、pytest；未执行前端构建和 `frontend/tests/purchaseOrdering.test.ts`。前端 package.json 也没有测试命令。本次手动检查通过，但日后提交不能依赖它自动保护。

### 范围缺口：不是所有零售系统功能都已存在

当前没有销售退货/退款、真实支付、进货取消/退供/部分签收、门店库存调拨、正式盘点单流程、报表文件导出、考勤工资等完整实现；销售主表也未关联收银员。它们应视为可能的后续需求，不能在原始需求不明时直接认定为必须补齐的缺陷。

AI 工具当前主要覆盖商品、库存、供应商、进货、销售、员工、折扣与概览查询/修改；总部管理和联络事项没有相应完整 AI 工具集。持久会话有历史列表和分页读取，但没有会话删除/重命名 API。是否扩展取决于目标范围。
